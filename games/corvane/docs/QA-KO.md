# Corvane QA

[English](QA.md)

기획서의 QA 요건: 모든 데모 빌드와 본 빌드를 **melonDS**에서 확인하고, 검수 기록에
melonDS 버전·데모 이름·기대 화면 설명을 남깁니다.

## 데모 빌드 공통 규칙

- 빌드: `./build.sh DEMO=<이름>` → `corvane-<이름>.nds` (`./build.sh demos`로 전부)
- 화면: 메인 화면 text BG 콘솔에 데모 이름과 결과가 나옵니다(3D 데모는 BG1 콘솔).
- 체크포인트: 시작 후 120프레임에 화면을 완성하고 `CHECKPOINT` 두 줄을 출력합니다.
  같은 값이 메인 RAM `0x0237F000`에 기록됩니다.

```
0x0237F000 u32 magic   = 0x52455643 ("CVER")
0x0237F004 u32 demo_id = FNV-1a 32 해시(데모 이름)
0x0237F008 u32 frame   = 체크포인트 시점의 VBlank 수
0x0237F00C u32 values[13] (데모마다 아래 표의 값)
```

- QA 로그 결과 블록(`io-qalog`와 이어지는 자동 QA 모드): 주소와 배치는 같고 `demo_id` = `QARN`
  (0x4E524151). `values[0]` 판정(1 PASS, 2 FAIL), `[1]` 로그 줄 수, `[2]` SD 플래그,
  `[3]` 마지막 체크포인트 해시, `[4]` 체크포인트 수, `[5]` 랙 프레임, `[6]` 세이브 플래그
  (bit0 칩 쓰기 검증, bit1 SD 미러 읽기 검증), `[7..12]` 게임별.
  로그 자체는 SD 카드의 `<드라이브>cleancart/<게임>/qa-<날짜>-<시각>.log`이고
  `tools/qa/parse_log.py`로 검사합니다.
- 입력이 필요한 데모(sys-keys, io-touch, io-power, io-rtc, io-firmware)는 체크포인트 뒤에도
  화면을 계속 갱신합니다.

## 자동 QA 실행

숨김 모드(출시 ROM과 같은 ROM): 타이틀 화면에서 **L+R+X+Y를 120프레임 누르고 있으면** 게임이
스테이지 1~5, 엔딩, 크레딧을 스스로 플레이하고 기록 화면에서 끝납니다. 끝나면 카트에 있던 원래 세이브(설정 슬롯과 마지막 런 리플레이 영역)를 복원합니다. 보스 HP ×0.1, 피격해도
잔기가 줄지 않는 정도의 숫자만 바뀌고, 이펙트·사운드·세이브는 그대로입니다. SD 카드가 있는
플래시카트에서는 `cleancart/corvane/qa-<날짜>-<시각>.log`와 `save-<n>.bin`을 쓰고, 어느
경우든 `QARN` 결과 블록을 채웁니다. 헤드리스 실행: `SDDIR=out/mds/x tools/melonds/mds.sh run
games/corvane/corvane.nds 20000 out/mds/x "60:A,200:A,500:L:140,500:R:140,500:X:140,500:Y:140"`
후 로그를 `tools/qa/parse_log.py`로 검사합니다.

| 환경 | 결과 (2026-11-11, 이 트리의 빌드) |
|---|---|
| melonDS 1.1 헤드리스, 소프트웨어 렌더러, SD 이미지 | ✅ 13,725프레임에 `RESULT PASS reason=credits`, 스테이지 체크포인트 5개, 세이브 미러 6개 읽기 검증 일치(`chip_type=-1`: 홈브루 실행이라 세이브 칩 없음) |
| 같은 ROM 두 번째 실행 | ✅ 체크포인트 해시 전부 동일(`tools/qa/compare.py`) |
| DeSmuME 헤드리스(SD 없음) | ✅ `QARN` 블록 판정 1, 마지막 상태 해시 `37db96a8` = melonDS(랙은 다름, 비교 대상 아님) |
| 실기 DS Lite + R4 | 아직 안 돌림 |

## 판정(`expected.json`, `tools/judge.py`)

각 데모의 결과 블록을 `tools/judge.py`가 `expected.json`과 대조합니다(항목 116개, 75개 데모 중 59개). 항목마다
1~4의 `level`과 `level_basis`가 있으며([docs/LEVELS-KO.md](../../../docs/LEVELS-KO.md)), 레벨은 판정에 영향을 주지 않습니다.

| 종류 | 판정하는 것 | 예 |
|---|---|---|
| (a) 자체 검사, 문서화된 상수 | 오류 수 0, `sqrt(10^12)` = 1000000, CRC 일치, 폴리곤 2048 | sys-wram, sys-dma-*, sys-bios, sys-math, 3d-limits |

## 캡처 경로 교차 검증 (acc-dual)

`acc-dual`은 두 화면 모두 3D를 보여 줄 때와 폴리곤 한도를 넘는 장면을 그릴 때 쓰는 디스플레이 캡처
기법 두 가지를 돌립니다. melonDS GL 렌더러에서 깨진다고 보고된 경로입니다:
[#2618](https://github.com/melonDS-emu/melonDS/issues/2618)(master에서 두 패스 렌더링이 깜빡임),
[#2619](https://github.com/melonDS-emu/melonDS/issues/2619)(캡처된 프레임이 업스케일되지 않음).

1. 0–7번 호출에서 프레임 지연을 잽니다. 호출 번호를 색으로 나타낸 전체 화면 사각형을 한 번 캡처합니다.
2. 8–55번 호출에서 블록 도시를 정면도(위, 빨간 클리어)와 평면도(아래, 파란 클리어)로 번갈아 보여 줍니다.
   엔딩과 같은 방식입니다.
3. 56–59번 호출에서 더 큰 도시를 한 패스로 그려 넘침을 확인합니다.
4. 60번 호출부터 큰 도시를 왼쪽·오른쪽 두 패스(절두체 반쪽, 뷰포트 반쪽, 클리어 알파 0)로 그립니다.
   두 번째 캡처가 3D와 뱅크 B의 첫 패스를 EVA = EVB = 16으로 섞고, 엔진 B가 합성 결과를 위 화면에
   보여 줍니다. 체크포인트 뒤에는 A로 양화면 보기와 두 패스 보기를 바꿉니다.

클리어 색은 폴리곤 목록과 함께 latch되므로, 캡처 설정이 아니라 지오메트리를 보내는 호출에서 씁니다.

결과 블록: `values[0]` 지연, `[1]` D의 정면 클리어 픽셀 << 16 | C의 평면 클리어 픽셀, `[2]` 합성
왼쪽 << 16 | 오른쪽 픽셀, `[3]` 플래그(비트 0 시점이 맞는 뱅크에, 1 한 패스는 넘침, 2 두 패스는 들어감,
3 합성에 양쪽 절반이 있음, 4 지연 0 또는 1. 실기라면 `1f`), `[4..6]` 한 패스·패스 1·패스 2의
폴리곤 | 넘침 << 16, `[7]` 합성 해시, `[8..9]` D와 C의 해시, `[10]` 교차 카운트(0이어야 함).

## 같은 화면 두 패스 (acc-split)

`acc-split-*` 일곱 빌드는 [#2618](https://github.com/melonDS-emu/melonDS/issues/2618)을 쫓습니다.
master에서 그 홈브루는 움직이는 분할선 왼쪽이 거의 두 프레임에 한 번 검게 나옵니다(이슈 첨부 영상에서
측정, 1.1은 정상). 매 프레임 분할선 한쪽은 직접 렌더하고(절두체 반쪽, 뷰포트 반쪽), 다른 쪽은 이전
프레임 캡처에서 가져옵니다. 벽과 바닥이 모든 픽셀을 덮고 배경색은 회색이라, 위 화면의 회색(또는 검은)
픽셀은 캡처 쪽이 비었다는 뜻입니다. 100–107프레임(hdma는 150–153), 위 화면, headless:

| 캡처한 쪽을 되돌리는 방법 | 1.1 소프트웨어 | 1.1 GL / Compute | master `4ce2188` 소프트웨어 | master GL / Compute |
|---|---|---|---|---|
| `tex`: 직접 그린 패스 뒤에 다이렉트 컬러 텍스처 | ✅ | ✅ | ✅ | ✅ |
| `bg`: 3D 레이어 뒤에 16bpp 비트맵 BG3 | ✅ | ✅ | ✅ | ✅ |
| `relay`: 짝수 프레임 VRAM 디스플레이 모드, 홀수 프레임 그래픽 캡처 | ✅ | ✅ | ✅ | ✅ |
| `rear`: 3D 리어 플레인(클리어 비트맵, 텍스처 슬롯 2) | ✅ | ❌ 매 프레임 한쪽이 빔 | ✅ | ❌ 매 프레임 한쪽이 빔 |

### 리어 플레인

OpenGL 렌더러는 리어 플레인을 캡처가 아니라 에뮬레이트된 VRAM 사본(`VRAMFlat_Texture`)으로
만듭니다. master에서는 CPU가 그 뱅크를 건드리기 전까지 캡처가 GPU 텍스처에만 있어서, CPU 접근이
있으면 고쳐집니다. 1.1은 그래도 안 됩니다. 빈 쪽이 좌우로 번갈아 나오는 건 패스가 번갈기 때문입니다.
이 문제는 별개의 발견이고, melonDS 이슈에서는 찾지 못했습니다.

### 캡처 뱅크에서 HBlank DMA: #2618의 구조

`hdma`는 #2618 홈브루의 방식입니다. 패치한 headless master 코어로 그 홈브루의 레지스터 쓰기를 읽어
알아냈습니다. 엔진 A(3D)는 아래 화면에 있고 캡처에만 쓰입니다. 위 화면은 엔진 B의 16bpp 비트맵
BG2이고, 반복 HBlank DMA가 HBlank마다 512바이트 한 줄씩 캡처 뱅크 D에서 채웁니다. BG2Y = −1이라
HBlank N에 복사한 줄이 N + 1번째 줄에 보입니다. 프레임은 번갈아 이렇게 돕니다.

| 프레임 | 뱅크 D로 캡처 | DMA가 읽는 줄 | 실기에서 위 화면 |
|---|---|---|---|
| 짝수 (P) | 3D만 (오른쪽 패스) | 한 줄 앞, 캡처가 덮어쓰기 전 | 직전 완성 그림 |
| 홀수 (Q) | 3D(왼쪽 패스) + VRAM D, EVA = EVB = 16 | 방금 캡처된 그 줄 | 새 완성 그림 |

melonDS master는 캡처를 GPU에 두고 VBlank(또는 레지스터가 바뀔 때)에 실행합니다. 캡처 중인 뱅크를
CPU나 DMA가 처음 읽으면(VCount 0) 캡처 텍스처를 에뮬레이트된 VRAM으로 한 번 복사하고 동기화됨으로
표시하며, `READING VRAM AS IT IS BEING CAPTURED TO`를 로그에 남깁니다. 그래서 DMA는 한 패스만 들어
있는 이전 프레임 캡처를 복사하고, 왼쪽이 빕니다. 이 ROM에서는 빈 곳이 64줄 캡처 블록 단위로 나옵니다
(한 프레임은 0–127줄, 다음 프레임은 128–191줄). 매 스캔라인마다 그 줄까지 캡처를 실행하고 끝나지 않은
캡처는 동기화됨으로 표시하지 않는 디버그 패치를 넣으면, 이 ROM과 그 홈브루 모두 구멍이 사라집니다.
1.1과 소프트웨어 렌더러는 캡처를 줄마다 VRAM에 쓰므로 정상입니다.

ROM이 스스로 판정합니다. 마지막 16프레임 각각이 끝난 뒤 서브 BG(뱅크 C)를 읽어 네 줄마다 투명하거나
검은 픽셀을 셉니다. 결과 `values[3]`은 구멍 난 프레임 수로, 블렌드 프레임 << 8 | 캡처 전용 프레임입니다.
`0000`이면 통과이고, master GL과 Compute는 `0808`입니다.

이슈 #3. 위 결과는 모두 이 검수에서 나왔습니다.

- **melonDS:** 공식 macOS 유니버설 앱 1.1(Apple Silicon). JIT 끔, 소프트웨어 렌더러, 다이렉트 부트, 사용자 이름 "melonDS"인 생성 펌웨어로 실행했습니다.

### 참고

- **세이브 칩:** melonDS는 헤더 게임 코드로 칩을 정하기 때문에 모든 빌드에 8 KB EEPROM이 붙습니다.
  - EEPROM·FRAM 빌드는 이를 감지해 리플레이를 0x0800에 최대 6140바이트로 저장합니다.
  - FLASH 빌드는 이 칩에서 JEDEC ID가 없으므로 리플레이를 7675바이트로 제한합니다.
  - 보통의 스테이지 플레이는 들어갑니다. 연사 스크립트 플레이는 넘쳐서 리플레이를 남기지 않지만, 슬롯은 그대로입니다.
- **DeSmuME가 놓친 이유:** MPU가 없고, 쓰기 전용 레지스터를 다시 읽을 수 있고, 디스플레이 동기 DMA를 처리하지 않고, 폴리곤 RAM 레지스터를 0으로 읽고, 세이브 칩을 `SAVETYPE`으로 정합니다.
- **DeSmuME와 다르지만 정상인 값:**
  - `sys-timer`는 120프레임 시점 1초·15박으로 DeSmuME와 같습니다.
  - `io-firmware`, `io-touch`는 에뮬레이터마다 펌웨어가 다릅니다.
  - `sys-irq`, `sys-ipc` 카운트는 몇 정도 차이 납니다.
- **확인하지 않은 것:**
  - 실기와 DSi
  - 새 헤더 게임 코드에서의 플래시카트 커널·TWiLight Menu++
  - melonDS JIT·OpenGL 렌더러
  - 사람이 직접 듣는 확인

## 자동 스모크 테스트 기록 (DeSmuME)

melonDS 검수 전에, 이 저장소를 만든 세션에서 헤드리스 DeSmuME 0.9.12(py-desmume 0.0.9,
x86_64 컨테이너)로 다음을 확인했습니다. melonDS 검수를 대신하지는 않습니다.

- 데모 65종: 모두 120프레임 체크포인트 도달(결과 블록 magic 확인). DeSmuME는 폴리곤 RAM
  사용량과 오버플로 플래그를 보고하지 않아 `3d-limits` 값은 0으로 나옵니다.
- 세이브: EEPROM 64 KB / FLASH / FRAM 각각 쓰기·검증·재로드 성공.
- 카트 DMA: probe.bin CRC가 NitroFS 경로·기대값과 일치.
- 본 빌드: 부팅부터 스테이지 1~5, 각 보스, 결과, 양화면 3D 엔딩, 스태프 롤, 기록 저장까지 진행.
- 결정론: 스테이지 1을 입력과 함께 녹화한 판과 기록 화면에서 재생한 판의 스테이지 상태
  메모리(CvStage, 25.5 KB)가 300·600프레임에서 같음(다른 바이트는 힙 포인터와 메시지 문자열뿐).
